# RFC-0032: Git

Status: Draft — body not audited against settled decisions (see docs/decisions.md)

## Abstract

Git is a fundamental primitive in Aidos (RFC-0010: Projects). Every project is backed by a Git
repository. Sessions work with Git via the Tool Broker (RFC-0030). Git operations include
reading history, creating commits, branching, merging, and pushing/pulling.

Two decisions that this RFC previously left open are settled in **RFC-0053**, and everything
below should be read against them:

1. **The backend is JGit on every platform profile** — pure JVM, no native dependency, works on
   Android. One implementation everywhere, so a project behaves identically on a phone and a
   desktop.
2. **JGit does not implement `git worktree`.** Worker isolation therefore uses **treeless
   workers** (RFC-0049): a worker builds a commit directly against the object database with an
   in-memory index and never materializes a second working tree. On a phone this is strictly
   better than a worktree — no duplicated checkout, no disk cost, no working-tree conflicts —
   and it produces the same artifact, a reviewable commit on a `refs/aidos/**` ref.

Worktrees are **not** the isolation mechanism on any profile. A DESKTOP worktree remains a
possible optimization for the one case that genuinely needs a second working tree — running a
build against a worker's changes without disturbing the user's — behind the same
commit-artifact contract. It is an optimization, and nothing in the architecture may depend on
it existing.

Aidos also never runs repository hooks, never rewrites history unasked, and never force-pushes
(RFC-0053).

## Motivation

Git is the industry standard for version control. Its advantages:

1. **Decentralized**: No central server required.
2. **Distributed history**: Full history available locally.
3. **Merge capability**: Handle branching and conflicts.
4. **Audit trail**: Commits record who did what when.
5. **Tooling**: Rich ecosystem of Git tools and workflows.

By making Git central, Aidos inherits these benefits. Decision history, Intent Graph changes, and resource evolution are all Git commits.

## Goals

1. **Define Git tool in Tool Broker**: What Git operations are available?
2. **Establish branching model**: How do sessions use branches?
3. **Specify worker isolation**: how a worker produces a reviewable commit without a checkout.
4. **Clarify commit semantics**: How are commits created and attributed?
5. **Define merge and diff support**: How are conflicts handled?
6. **Explain history querying**: How do sessions understand project evolution?

## Design

### Git Tool Interface

Sessions invoke Git via Tool Broker:

```
Tool: "git"
Capabilities:
  - git:read         (read-only: log, diff, status, branch list)
  - git:write        (create commits, branches, merge)
  - git:push         (push to remote)
  - git:fetch        (fetch from remote — never touches the working tree)
  - git:merge_ff     (fast-forward only; cannot conflict by construction)
  - git:switch       (change branch — destroys uncommitted work, RFC-0053)

Example:
  Session.invoke("git:write", {
    operation: "commit",
    message: "Add tests for caching",
    author: "Session S1"
  })
```

### Worker isolation, without a checkout

Each worker gets a ref, not a directory:

```
Base: feature/payment
  ├─ Worker W1 → refs/aidos/workers/<w1>   auth
  ├─ Worker W2 → refs/aidos/workers/<w2>   tests
  └─ Worker W3 → refs/aidos/workers/<w3>   docs

Each builds a tree in an in-memory index and commits against the object
database. None touches the working tree. Results are merged into the base.
```

This gives everything the worktree model gave — isolation, parallelism, cheap cleanup by
deleting a ref — without a second copy of the tree on a device that has room for one. The
artifact is identical: a reviewable commit.

Worker refs are pruned when the session is archived, so they never appear in the user's branch
namespace (RFC-0053).

### Fetch, and why there is no `pull`

`git pull` is fetch plus merge, and the merge half is the problem. A merge that conflicts leaves
the working tree in a three-way state that needs resolution, and resolving a real conflict is the
one Git operation that categorically does not fit the hunk-card model (D25) — you are choosing
between two versions of a region, not accepting or rejecting one change. Nothing in RFC-0050
specifies that surface, and a project stuck mid-conflict on a phone with no way out is worse than
an operation that was never offered.

So the MVP splits it:

| Operation | Available | Why |
|---|---|---|
| `git:fetch` | everywhere | Writes only to the object DB and remote refs. Cannot conflict, cannot touch your working tree. You can see what is upstream and diff against it |
| `git:merge_ff` | everywhere | A fast-forward cannot conflict — it moves a ref to a descendant commit |
| three-way merge | **DESKTOP only** | Needs a conflict-resolution surface that does not exist on MOBILE, and is reported unavailable rather than attempted |

Fetching still produces the "large unreviewed diff" case D25 names, but at a moment of the user's
choosing rather than mid-Run.

### Branch switching

`git:switch` is a **destructive operation** and is typed as one:
`Mutate(IN_PROJECT, reversible = false)`.

Uncommitted changes are discarded, after a warning naming the files and line counts, with
*commit first* offered as the primary action. RFC-0053 specifies the behaviour and what a switch
invalidates — review marks, and any approval a Run was parked on. Because it is irreversible, it
is excluded from D26's benign class: it can never be approved by a glance or a single spoken
word.

### Branching Model

Sessions use Git branches to organize work. Workers commit to their own refs and never check
anything out:

```
User creates project:
  - Main branch initialized

Driver session:
  - Creates feature branch: feature/X
  
Worker session 1:
  - Builds against the object DB on refs/aidos/workers/<w1>
  - Commits changes
  
Worker session 2:
  - Builds against the object DB on refs/aidos/workers/<w2>
  - Commits changes
  
All changes merge back to feature/X
Feature complete, merge to main
```

### Commit Attribution

Commits are attributed to sessions:

```
Session S1 commits:
  Author: "Session S1 (Driver)"
  Committer: "Aidos"
  Message: "Implement user auth [Session S1]"
  
Audit trail:
  Git shows which session made each change
  User can review session work
```

### History and Diff

Sessions query Git history:

```
Session queries: "What changed in payment.rs?"
Git tool:
  1. git log payment.rs
  2. git diff per commit
  3. Return change history
  
Session queries: "What did session S1 do?"
Git tool:
  1. git log --author "Session S1"
  2. Return all commits by S1
```

### Future: PR Workflows

Future versions could support pull requests:

```
Session creates PR: feature/X → main
Workflow:
  1. Automated tests run
  2. Code review (if enabled)
  3. Merge to main
```

## Data Model

```
GitTool extends Tool {
  repository_path: Path             # Project root
  
  branches: Map<BranchName, CommitHash>
  worker_refs: Map<SessionId, RefName>   # refs/aidos/workers/<id>
  
  current_branch: String
}
```

Diffs are returned as **structured hunks with stable identity** — `(path, base blob hash, hunk
index)` — never as a formatted string (D25). A phone that receives a diff as text has to parse it
back into structure on the device with the least CPU, and every frontend reimplements it.

## Security

Git tool enforces capabilities:

- `git:read`: View-only operations.
- `git:write`: Can create commits.
- `git:push`: Can push to remote.
- `git:fetch`: Can fetch. Safe — it writes only to the object database and remote refs.
- `git:merge_ff`: Can fast-forward. A merge requiring a real three-way resolution is
  **unavailable on MOBILE** and says so through `AvailabilityReport` (RFC-0049).
- `git:switch`: Can change branch, discarding uncommitted work.

Only sessions with appropriate permissions can perform operations.

## MVP Scope

MVP includes:

1. **Read operations**: log, status, diff, show.
2. **Write operations**: commit, branch, checkout.
3. **Worktree management**: create, delete, switch.
4. **Basic merge**: merge branches, handle simple conflicts.
5. **Push/pull**: Sync with remotes.

Not included:

- PR workflows (future).
- Interactive rebase (future).
- Cherry-pick (future).
- Advanced conflict resolution (future).

## Future Work

- **PR automation**: Create and manage PRs.
- **GitSema integration** (RFC-0015): Index code structure alongside Git.
- **Bisect support**: Find problematic commits.
- **Submodule support**: Manage Git submodules.
- **LFS support**: Handle large files.
